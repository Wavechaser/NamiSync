NamiSync v0.1.0 — source and build directions

The builder produces development artifacts. Candidate acceptance and external
delivery remain separate release checkpoints.

Source identity
---------------
Distribute the corresponding NamiSync source ZIP, SHA256SUMS.txt,
source-identity.json, bundle-identity.json and build-environment.txt alongside
the executable ZIP. Do not substitute a newer source checkout for the source
that produced a published executable. Verify each archive against SHA256SUMS.txt.
source-identity.json records the commit and per-file source hashes;
bundle-identity.json records the files in the executable bundle.

The source ZIP includes NamiSync's editable Python, JavaScript, CSS, HTML,
artwork, build specification, requirements and license. The reviewed ICO is an
input: ordinary builds do not rasterize it from SVG. The source repository is:
  https://github.com/Wavechaser/NamiSync
Full documentation and tests live in that repository at the recorded commit.
NamiSync is GPL-3.0-or-later. Upstream components retain their own terms; the
THIRD-PARTY-NOTICES.txt identifies their versions, sources and license texts.

Upstream component source
-------------------------
The app uses unmodified locked upstream package source and native components.
Embedded asset selections/adaptations are identified in the individual notices.
The notice file gives exact versions and pinned source/license URLs.
tools/packaging/notices/manifest.json in this
source ZIP also records the supplement files and source wheel hashes. Obtain the
locked upstream distributions with pip download --require-hashes using the
included requirements and bootstrap files. Wheels are ZIP archives: Python
modules inside them are source, not just compiled executables.

In particular, setuptools 84.1.0's wheel contains the exact MPL-2.0-covered
source under setuptools/config/_validate_pyproject/ and schema source under
setuptools/config/. Obtain that wheel at:
  https://pypi.org/project/setuptools/84.1.0/#files
Extract those directories together with their NOTICE files. The wheel's SHA-256
is pinned in tools/packaging/bootstrap.txt. These unmodified files include copied
validate-pyproject source and generated fastjsonschema code; their notices retain
the MPL-2.0 and BSD terms. The same wheel contains all the selected setuptools
vendored Python sources and licenses under setuptools/_vendor/.

Native-source starting points for the exact bundled versions:
  CPython 3.15.2: https://github.com/python/cpython/tree/v3.15.2
  Python external inputs: that tag's PCbuild/get_externals.bat
  OpenSSL 3.5.9: https://github.com/openssl/openssl/tree/openssl-3.5.9
  Python native dependencies: https://github.com/python/cpython-source-deps
    branches bzip2-1.0.8, libffi-3.4.4, mpdecimal-4.0.0,
    sqlite-3.53.4.0, xz-5.8.1.1, zlib-ng-2.2.4 and zstd-1.5.7
  Expat: CPython tag's Modules/expat (2.9.0)
  HACL* hash implementations: CPython tag's Modules/_hacl, compiled into
    python315.dll; retained MIT and Apache notices identify the vendored
    implementation and KaRaMeL support headers.
  BLAKE2 wrapper: CPython tag's Modules/blake2module.c (public-domain/CC0 code).
  CPython wrapper/runtime credits: Modules/_decimal/_decimal.c,
    Modules/_winapi.c and Python/getopt.c at the same CPython tag.
  pysqlite: CPython tag's Modules/_sqlite; retain its zlib-style notices when
    redistributing that source. The bundled SQLite engine is identified above.
  PyInstaller 6.22.3: https://github.com/pyinstaller/pyinstaller/tree/v6.22.3
    bootloader/zlib contains its statically linked zlib 1.3.2 inflate subset,
    separate from the CPython runtime's zlib-ng 2.2.4.
For cffi, xxhash, pythonnet and clr_loader native sources, obtain each pinned
version's source distribution/repository from the corresponding PyPI project
and the source references in the notices. The build consumes the locked Windows
wheels; the lock does not claim to reproduce their upstream compiler toolchains.
The xxhash 4.1.0 wheel contains xxHash 0.8.4 with x86 runtime dispatch. Its
source distribution contains the engine and dispatch files under deps/xxhash/.
The PyInstaller bootloader exception and runtime-hook terms are reproduced in
the notices. XZ contributes its 0BSD-licensed liblzma.
Microsoft binaries retain their distribution conditions; they are not relicensed
under NamiSync's GPL. Windows 11 supplies UCRT/API-set system libraries.
The CPython Windows installation license reproduced in THIRD-PARTY-NOTICES.txt
requires further distributors to require their distributors and external end
users to agree to terms protecting the Microsoft Distributable Code at least
as much as Microsoft's own requirements. Arrange that agreement before external
handoff (the R5 delivery prerequisite); merely including notices is not a grant
of redistribution rights. Consult the reproduced conditions for their exact
terms. They apply only to Microsoft Distributable Code, not to NamiSync or
Python itself, and do not change NamiSync's GPL license.

Build from the recorded repository commit
----------------------------------------
Use Windows x64, Git and CPython 3.15.2 x64. The release build uses the official
PSF Windows managed-runtime archive:
  https://www.python.org/ftp/python/3.15.2/python-3.15.2-amd64.zip
  SHA-256 d6da9c33a32cf111e1d52b91392c83ea6a808545b646e0557f66cb6d9ee76785
Verify its SHA-256 and extract it to a new directory before creating a virtual
environment. A compiler and Node are not required
by the portable build command. Node 24.22.1 is used for project verification.
The commands below assume python resolves to that CPython installation and
source-identity.json is in the starting directory:

  $revision = (Get-Content .\source-identity.json -Raw | ConvertFrom-Json).commit
  git clone https://github.com/Wavechaser/NamiSync.git NamiSync-source
  Set-Location NamiSync-source
  git checkout --detach $revision
  python -m venv build/package-env
  .\build\package-env\Scripts\python.exe -m pip install --require-hashes -r tools/packaging/bootstrap.txt
  .\build\package-env\Scripts\python.exe -m pip install --require-hashes --no-build-isolation -r tools/packaging/requirements.txt
  .\build\package-env\Scripts\python.exe tools/packaging/build.py build/portable-attempt-01

Stop if any command fails. Use a new environment and output directory per attempt.
The builder requires a clean committed checkout and the exact locked dependency
inventory. It records the source revision, selected Python executable hash,
platform, dependency versions and bundle hashes. Requirements specify download
hashes; proxy_tools is built from its source archive using the locked bootstrap.
The source archive's own instructions describe that revision's build behavior.

The source ZIP is also editable source, but contains no Git history. To build
from it, initialize a local Git repository, commit the extracted source and
your changes, and keep both the virtual environment and output outside that
source directory. Run its tools/packaging/build.py with that environment's
python.exe and a fresh absolute output path. This creates a new source revision;
do not label its output as the original maintainer's artifact. Obtaining the
recorded repository commit is the way to retain the original commit identity.

Verification and limits
-----------------------
The builder checks executable architecture/subsystems and CLI help. GitHub CI
runs ordinary tests/import contracts before building. Those checks do not
replace Windows 11 interactive startup, reviewed-copy, inventory, verification,
resource acceptance and close checks on the actual candidate.

Matching source and package locks do not promise a byte-identical complete ZIP.
Installer metadata and serviced Windows/SQLite DLLs can differ between hosts.
Compare recorded file identities and actual native-library origins before
reusing evidence. The freezer uses a bounded PATH and rejects native inputs from
outside the selected Python installation/build environment. Preserve
the original artifact when comparing a rebuilt one; do not overwrite evidence.

The build command neither signs the executables nor publishes a GitHub release.
v0.1.0 tester delivery is planned to be unsigned. Final asset names, checksums,
source/notice contents and handoff are approved at the candidate checkpoint.
