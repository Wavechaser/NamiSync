# M2 Proposal

This is the single index of proposed later features, not an implementation plan.
[FEATURES](FEATURES.md) owns product behavior and accepted future boundaries;
[ARCHITECTURE](ARCHITECTURE.md#m2--durable-sessions-and-queue-ownership) owns M2
direction. Accepted future outcomes remain binding; unrealized representation
and implementation recipes are reconsidered at first use under [AGENTS](../AGENTS.md).
Listing an outcome does not activate implementation or change current M1 limits.

- **Execution retries.** Let users retry a whole run, an executor failure or a reviewed safe subset after an unsuccessful execution.
- **Verification retries.** Let users retry terminal verification or verify remaining files, including standalone verification.
- **Verification open lookahead.** Investigate bounded concurrent first opens within automatic post-copy Verify before changing scheduling. Current serial fresh-file measurements do not establish a concurrency benefit. Preserve ordered classification/recording, honest native readback, bounded handle/buffer ownership and full worker settlement on control; review earlier observation and sharing-lock timing explicitly. Keep Execute→Verify sequential unless a separate workflow redesign is accepted. [PERFORMANCE](PERFORMANCE.md#verification-overlap-scope) owns the scope investigation. This proposal is not implementation authorization.
- **Session cleanup.** Let users explicitly clean up NamiSync-owned session temporary files and trash.
- **Small-file copy batching.** Design grouped parent-directory flushes and grouped ledger commits together. Preserve durability before acknowledging an item, and define how to settle published files after interruption, pause, cancellation or retry. The historical measured-volume saving for directory flushes alone was about 0.22 ms per 4 KiB file. [PERFORMANCE](PERFORMANCE.md) owns the measurement.
- **Unbuffered source reads.** Compare with buffered sequential reads on controlled cold-source workloads; implement only if end-to-end throughput or cache-pressure benefits justify it. Preserve small-file behavior, source admission, exact tail/hash semantics and bounded buffers; reconcile source/target alignment and capability fallback. M1 keeps buffered reads: its repeated-source results and standalone probes do not establish an integrated cold-read gain. [PERFORMANCE](PERFORMANCE.md) owns those observations.
- **Specific I/O errors.** Explain filesystem failures with specific typed causes beyond the generic `IO_ERROR` classification.
- **Durable task recovery.** Preserve tasks and recoverable session state across application closure or restart.
- **Command-result retention independent of task lifetime.** Allow routine repeated inventory Refresh, acknowledge and restore without eventually requiring task closure to reclaim command capacity. M1 shares 48 retained start/visibility-response slots across the desktop; task-owned entries survive until Close, so a long-lived inventory task can exhaust capacity for other tasks too. Design bounded retirement of settled results while preserving unresolved original-outcome recovery and preventing retired commands from executing again. Coordinate adapter replay and application receipt ownership; increasing the cap alone does not resolve the lifetime issue. The M1 limit and clean refusal remain unchanged until this design is accepted.
- **Durable queue.** Retain queued work across application restarts.
- **Native Fluent overlay scrollbars.** Integrate WebView2's environment option through the Windows host when the backend work is justified. The current pywebview path needs coordinated startup, early navigation/HTML-loading and rendering-test changes; retain the CSS approximation for M1.
- **Verify-only batches.** Batch standalone verification directories. The current Setup runner admits source/target pairs; extending it to single-directory tasks belongs with a reviewed M2 Setup change.
- **Disk usage view.** Answer “what exists here, and what is taking up space?” for a folder or volume, including target capacity shortfalls and `.synctrash` growth. It is a new page: a sunburst navigator beside a flat one-level table of logical sizes, built from a retained directory-aggregate tree and a listing-only walk. It is read-only, makes no ledger writes, and has no mutation path. [DISK_USAGE_STUDY](DISK_USAGE_STUDY.md) records the user's 2026-11-15 direction, constraints and remaining questions. This study is not implementation authorization.
- **Compare page.** Answer “what exists in A and B, and how do they differ?” without planning a sync. It may share the disk usage view's two-pane layout, and it is a natural home for checksum adoption. Its outcome definition is still needed.
- **Shell actions.** Copy Path, Open in Explorer and Properties for rows on every page, with optional click-through. Each action resolves a server-owned node id to a path on the host side; the browser never supplies path text. No file is ever launched, and NamiSync performs no mutation. On Plan, side-labelled Source and Target actions avoid an implicit side choice. Missing items keep only Copy Path and Open containing folder. [DISK_USAGE_STUDY → Shell actions](DISK_USAGE_STUDY.md#shell-actions) holds the policy and cost notes.
- **Checksum adoption.** Copy content evidence from one location to another for metadata-equal pairs (no-op pairs), so existing duplicate backups gain checksums without hashing. The next Verify confirms or mismatches them. Sync execution is the natural first home: each selected paired no-op already re-checks both live stats against the review and calls `record_noop` ([RECORDER](RECORDER.md)), so adoption would extend that recording as a reviewed, fingerprinted plan option, with the adoptable count shown in review. A compare page could reuse the same primitive later, possibly in either direction. The origin's evidence must be current: its attested stats match its current observation and carry no invalidation. The receiving row must have no evidence; a different existing digest is never overwritten and is reported as disagreement. Recording uses the conditional primitive. Adopted evidence gets a new provenance naming its origin. It never advances `last_verified_at`, and the state stays unverified. Baseline skips it, so Verify is the check, and a later mismatch is labelled as differing from the adopted origin. The row then states what was observed (a metadata match plus the origin's evidence), not that target bytes were read, which preserves never-wrong-only-behind. A new `Provenance` value is a core, ledger and history contract change, and it needs a decision on the evidence epoch.
- **User-defined sync pair presets.** Create, customize and persist reusable pairs that otherwise populate Setup and use availability checks like history-derived recent pairs. Persistent records and bridge commands are new work; presets do not retain admission or execution authority.
